# Day-ahead forecasting of French electricity consumption

[![CI](https://github.com/karissa410/conso-forecast/actions/workflows/ci.yml/badge.svg)](https://github.com/karissa410/conso-forecast/actions/workflows/ci.yml)

Forecast, at the end of each day, the national electricity consumption of France for every
hour of the next day, using only open data: RTE's eCO2mix consumption records, hourly
temperatures from Open-Meteo, and the French holiday calendar. Two naive baselines, a
regularised linear model and a tuned LightGBM model are compared on a held-out test year.

The whole pipeline, from the download to the report, runs with one command (`make all`).

## Problem

Electricity cannot be stored at scale, so production must match consumption at every
moment. Producers, traders and the grid operator therefore need a forecast of
tomorrow's consumption, hour by hour. Consumption in France is driven by:

- **temperature**: a large share of homes are heated electrically, so cold days push demand up sharply;
- **the calendar**: hour of day, weekends, public holidays, "bridge" days, the Christmas period;
- **inertia**: today's consumption is a strong hint about tomorrow's.

## Method

**Forecasting setup.** The forecast for the 24 hours of day D+1 is issued at the end of
day D. Features built from consumption only use data from day D or earlier; a unit test
checks this by modifying future values and verifying that the features do not change.

**Time grid.** Data is cleaned onto a French local-time grid with exactly 24 hours per
day (on daylight-saving days the repeated hour is averaged and the missing hour
interpolated), so "the same hour yesterday" is always an exact 24-step shift.

**Cleaning.** Duplicate timestamps are dropped, physically implausible values are set to
missing, sub-hourly records are averaged per hour, and only gaps of up to 3 hours are
interpolated. A data-quality summary is written to `reports/results/data_quality.json`.

**Features** (`src/conso_forecast/features.py`):
- calendar: hour, day of week, month, smooth day-of-year, weekend, public holiday, bridge day, Christmas period;
- lags: same hour 1, 2 and 7 days earlier; mean, minimum, maximum and last value of day D; 7-day mean;
- weather: temperature, temperature smoothed over about a day (thermal inertia of buildings), daily mean, heating and cooling degrees.

**Evaluation protocol** (`src/conso_forecast/evaluation.py`): a strictly chronological
split.

| Set | Period | Use |
|---|---|---|
| Train | 2015 – 2023 (first COVID-19 lockdown removed) | fit models |
| Validation | 2024 | choose models and hyperparameters |
| Test | 2025 | final score, computed once |

Metrics: MAE (MW), RMSE (MW) and MAPE (%), computed on the hours where every model has
a prediction.

**Models.**
1. Baselines: same hour on the previous day; same hour one week earlier.
2. Ridge regression (one-hot calendar, standardised numeric features); regularisation
   strength chosen on the validation year.
3. LightGBM, tuned by random search (20 configurations) with early stopping on the
   validation year.

Every configuration is tracked in MLflow; the selected ones are refit on train +
validation before the test evaluation. RTE's official day-ahead forecast is shown as an
external reference only: it is never used as an input.

## Limitations

- **Observed weather.** Temperatures are reanalysis observations of the target hour. In
  operations one would use a temperature *forecast*, so real-world errors would be higher.
- **Midnight issue time.** Market forecasts are needed around noon on day D; this
  simplified setup gives the model 12 more hours of information.
- **National level only**, with a simplified population-weighted temperature from ten cities.
- **Structural changes** (the 2022–2023 energy-saving effort, electrification) and rare
  events are only partly captured by the lag features.

## Reproduce

Requirements: [uv](https://docs.astral.sh/uv/getting-started/installation/) (it installs
the right Python version itself), Git, and optionally `make`.

```bash
git clone https://github.com/karissa410/conso-forecast.git
cd conso-forecast
make install   # creates .venv with the exact versions of uv.lock
make all       # download -> clean -> eda -> train -> evaluate -> analyze -> report
```

Without `make` (for example on Windows): `uv sync` then `uv run conso-forecast all`.
Each step can also be run on its own: `uv run conso-forecast <step>` (see `make help`).

The download takes a few minutes (the Open-Meteo free API is rate-limited); training takes
a few minutes on a laptop. Results, figures and the report are written to `reports/`.

To browse the experiments: `make mlflow-ui`, then open <http://127.0.0.1:5000>.
